### 現状の課題（本開発で是正する）

1. **RLSが全開放**。anon keyはビルド成果物に含まれる公開情報のため、第三者が見積を全件取得し得る。→ **2026-07-26: 利用者が代表のみのため現状維持と判断**（§12参照）。供花の公開サイト側は別途、anonに直接アクセスさせない構成にした（§2.2）
2. `customer_info` がJSONBのため、顧客横断の検索・集計ができない
3. 商品画像を保持する仕組みがない（要件②と供花で共通して必要）

## 2. 供花発注システム

### 2.1 構成

```
┌─────────────────────────┐        ┌──────────────────────────┐
│ 供花サイト（新ドメイン）   │        │ 見積システム（既存）        │
│ VPS + Nginx             │        │ 既存サーバー               │
│ 静的ファイル（Viteビルド）  │        │ /  と /admin             │
└───────────┬─────────────┘        └────────────┬─────────────┘
            │                                    │
            │  Supabase Edge Functions           │
            │  （決済・メール・注文確定）           │
            ▼                                    ▼
        ┌────────────────────────────────────────────┐
        │            Supabase（共通DB）                │
        │  plans / items / estimates / customers /    │
        │  funerals / flower_products / flower_orders │
        └────────────────────────────────────────────┘
                            │
                   ┌────────┴────────┐
                   ▼                 ▼
                Stripe          メール配信
```

**方針**: VPSは静的ファイル配信のみ（Nginx）。Stripe決済とメール送信は **Supabase Edge Functions** で処理する。

- 理由1: Stripeの秘密鍵をブラウザに置けないため、サーバーサイド処理が必ず必要
- 理由2: VPSにNodeを常駐させると、プロセス監視・OS更新・SSL更新などの保守が増える。Edge Functionsなら障害点を減らせる
- 理由3: Stripe Webhookの受け口となる公開HTTPSエンドポイントがそのまま得られる

> VPS上にNode APIを立てる構成も可能。その場合は保守運用の担当を決める必要がある。

### 2.2 セキュリティ方針（重要）

公開サイトから **anon key で直接DBに読み書きさせない**。

| テーブル | anonからの直接アクセス | 経路 |
|---|---|---|
| `flower_products` | SELECT のみ許可（`is_active = true`） | 直アクセス可 |
| `funerals` | **不可**（故人名・喪主名は個人情報） | DB関数 `funeral_public_lookup` がトークン検証して公開可能項目のみ返す |
| `flower_orders` | **不可** | DB関数 `create_flower_order`（SECURITY DEFINER）が作成 |
| `estimates` / `customers` | **不可**（要是正） | 認証済みスタッフのみ |

金額は必ず **サーバー側で再計算**する（フォームから送られた金額を信用しない）。

## 3. 見積システム ①③（顧客DB + TOP画面）

### 3.1 DB設計（案）

```sql
CREATE TABLE customers (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  customer_no    text UNIQUE,          -- 顧客番号（連番）
  name           text NOT NULL,        -- 顧客名（ご葬家名）※管理の「箱」
  phone          text,
  postal_code    text,
  address        text,
  note           text,
  created_at     timestamptz DEFAULT now(),
  updated_at     timestamptz DEFAULT now()
);

ALTER TABLE estimates ADD COLUMN customer_id uuid REFERENCES customers(id);
CREATE INDEX ON estimates (customer_id);
```

### 3.2 挙動

- 見積作成時に顧客名が入力されたら、`customers` を自動作成して `estimates.customer_id` に紐付け
- 顧客一覧画面から手動でも顧客を作成可能
- **既存の宙ぶらりん見積**（`customer_id` が NULL）は、後から顧客情報が入った時点で紐付け。管理画面に「未紐付け見積一覧」を用意して手動紐付けもできるようにする
- 既存 `estimates` は `customer_info->>'applicantName'` 等をもとに移行スクリプトで顧客レコードを生成
- 見積番号の連番は現行どおり維持

## 8. P2 実装内容（供花 公開サイト）

### 追加したファイル

| ファイル | 内容 |
|---|---|
| `migrations/005_flower_public_api.sql` | 公開サイト用のDB関数（`funeral_public_lookup` / `create_flower_order`）とカード決済フラグ |
| `vite.flower.config.ts` | 供花サイト専用のビルド設定（出力先 `dist-flower/`） |
| `flower/index.html` `flower/main.tsx` `flower/App.tsx` | 公開サイト本体 |
| `flower/styles.css` | 公開サイトのスタイル（見積システムとは独立） |
| `flower/lib/api.ts` | DB関数の呼び出しとエラー文言の変換 |
| `flower/components/*.tsx` | 葬儀情報 / 商品一覧 / 申込フォーム / 確認 / 完了 / 通知 |

### anon から直接テーブルを触らせない仕組み

Edge Functionsの用意を待たずにP2を進めるため、**Postgresの SECURITY DEFINER 関数**で代替した。

| 関数 | 役割 |
|---|---|
| `funeral_public_lookup(p_token)` | トークンを検証し、公開してよい葬儀情報＋受付状態（`open` / `closed` / `deadline_passed` / `not_found`）のみ返す |
| `create_flower_order(p_token, p_orderer, p_items, p_payment_method)` | 締切・受付状態を再チェックし、**価格を商品マスタから引き直して**金額を再計算のうえ注文を作成 |

`funerals` / `flower_orders` への anon の直接アクセス権は付与していない。クライアントから送られた金額は一切使用しない。

Stripe決済とメール送信はサーバー側の秘密鍵が必要なため、P3・P4でEdge Functionsを追加する。

### 画面フロー

```
/order/<token>
   ↓ funeral_public_lookup
[葬儀情報 + 商品一覧] → 商品モーダル（画像・名札・数量）
   ↓ カートバー
[お申込者さま情報 + お支払い方法]
   ↓
[ご確認]
   ↓ create_flower_order
[完了（注文番号を表示）]
```

受付状態が `closed` / `deadline_passed` / `not_found` の場合は、それぞれ専用のご案内画面を表示する。

### カード決済の扱い

Stripe未接続のため、`flower_settings.card_payment_enabled` を **既定 false** とした。オフの間、公開サイトには請求書払いのみ表示され、DB関数側でもカード決済を拒否する。P3でStripe接続が完了したら管理画面の「設定」からオンにする。

### 開発・ビルド

```bash
npm run dev:flower     # http://localhost:3100/order/<token> で確認
npm run build:flower   # dist-flower/ に出力
```

### VPSへの配置（P5で実施）

`dist-flower/` の中身をドキュメントルートへ配置し、Nginx でSPAフォールバックを設定する。

## 10. 見積から発注受付を作成（2026-07-26 追加）

葬儀情報を毎回手入力するのではなく、**既存の見積から故人名などを引き継いで受付URLを発行する**導線を追加した。

### 操作

`/admin` →「葬儀・発注受付」→ **「見積から受付を作成」**

1. 見積を検索（故人名・申込者名・見積番号）
2. 選択すると次の項目が自動で入る
   - 故人名 ← `customer_info.deceasedName`
   - 喪主名 ← `customer_info.chiefMournerName`
   - 告別式日時 ← `customer_info.funeralDate`（時刻は10:00を既定値として補完。画面で変更可）
   - 見積番号 ← `estimates.id`（`funerals.estimate_id` に保存）
3. 受付締切は告別式日時から自動計算される
4. 保存すると発注URLが発行される

### 補足

- **式場名・式場住所は見積に項目が無いため手入力**（必要な場合のみ）
- すでに同じ見積から受付を作成済みの場合は、重複作成せず既存の受付を開く
- 見積が無い葬儀のために「手動で作成」も残している

## 12. 要件① 顧客DBベース管理（2026-07-26 実装）

### DB

`migrations/007_customers.sql`

- `customers` テーブルを新設（顧客番号は `C-000001` 形式の連番）
- `estimates.customer_id` を追加して紐付け
- **既存の見積を自動移行**（申込者名 → 喪主名 → 故人名 の順に顧客名を決定。同名は1つの顧客にまとめ、電話番号・住所も引き継ぐ）
- いずれの名前も空の見積は `customer_id = NULL` のまま残し、画面から手動で紐付けられるようにした
- `estimates` に UPDATE ポリシーを追加（顧客の付け替え・情報修正のため）

### 画面

| 機能 | 場所 |
|---|---|
| 顧客の追加（箱だけ作る） | 顧客一覧 →「顧客を追加」 |
| 顧客情報の編集 | 顧客一覧の各行 / 顧客詳細の「顧客情報を編集」 |
| 顧客の削除 | 顧客一覧の各行（見積が紐づいている場合は拒否） |
| 見積単位の編集 | 顧客詳細・見積検索の各行「編集」 |
| 見積の顧客付け替え | 見積編集モーダルの「紐づく顧客」 |
| 未紐付け見積の紐付け | 顧客一覧下部「未紐付けの見積」 |

見積単位で編集できる項目: 故人名 / 葬儀日 / 申込者名 / 喪主名 / 電話番号 / 紐づく顧客

> `customer_info` と `content.customerInfo` の両方を更新しているため、編集内容は見積を呼び出したときの入力値にも反映される。

### 見積保存時の自動紐付け

見積の保存時に顧客名（申込者 → 喪主 → 故人）で顧客を検索し、**同名があれば再利用・無ければ自動作成**して紐付ける。
同名が複数ある場合は電話番号が一致するものを優先する。顧客名が空の場合は未紐付けのまま保存する。

顧客の紐付けに失敗しても見積の保存は続行する（後から画面で紐付けられるため）。

### RLSの方針（2026-07-26 判断済み）

`customers` は `estimates` と同じく **anon に SELECT / INSERT / UPDATE を許可**している。

見積画面を使うのが代表のみであるため、**当面はログイン必須化せず現状維持**とする方針で合意済み。
ただし anon key はビルド成果物に含まれる公開情報のため、URLと鍵を知る第三者は画面を経由せずデータを取得し得る。
利用者が増える、または外部に共有する段階になったら、見積画面のログイン必須化とあわせてRLSを閉じること。

## 13. 業者への発注書（2026-07-26 実装）

### 決定事項

- 供花業者は **当面1社固定**。設定に業者名とメールアドレスを持つ
- 発注書は **葬儀（＝故人）単位**で、その葬儀の全注文をまとめて1通送る
- 送信は受付締切後に管理画面から手動で実行（自動送信にはしていない）

### データの集約単位

```
葬儀（故人名・式場・告別式日時・受付締切）
 ├─ 注文A ─ 明細（商品・数量・名札）
 ├─ 注文B ─ 明細
 └─ 注文C ─ 明細
```

発注URLは葬儀ごとに発行されるため、そのURLから入った注文はすべて同じ葬儀にぶら下がる。
発注書はこれを集約し、**商品ごとの合計本数**と**設営順に通し番号を振った名札一覧**を本文に出力する。
キャンセル済み（`order_status = 'cancelled'`）の注文は除外する。

### 実装

| ファイル | 内容 |
|---|---|
| `migrations/008_flower_supplier.sql` | `flower_settings.supplier_name` / `supplier_email`、`funerals.purchase_order_sent_at` |
| `supabase/functions/_shared/mailTemplates.ts` | `buildPurchaseOrderMail`（葬儀単位で集約） |
| `supabase/functions/send-order-mail/index.ts` | `type: 'purchase_order'` を追加（スタッフのログイン必須） |
| 管理画面「葬儀・発注受付」 | 各行に注文件数・発注書の送信状況・送信/再送ボタン |
| 管理画面「設定」 | 業者名・業者のメールアドレス |

### 今後の検討

- 業者が複数になった場合は、カテゴリ別または商品別に業者を持たせる構成へ拡張する
- 締切到達時の自動送信（pg_cron などのスケジューラが必要）

## 14. 画面配置の変更（2026-07-26）

供花システムの運用機能をユーザー画面（見積システム側）へ移し、管理画面にはマスタと設定を残した。

### ユーザー画面（TOP画面から）

| 機能 | 内容 |
|---|---|
| 供花 発注URL発行 | 葬儀の作成（見積から引き継ぎ可）、URL発行・コピー、受付の開始/停止、業者への発注書送信 |
| 供花 発注者一覧 | 申し込み状況の確認、注文詳細、ステータス変更、請求書の送信、名札CSV出力 |

### 管理画面（`/admin`）

| 機能 | 内容 |
|---|---|
| 供花商品管理 | 商品の登録・編集・画像アップロード・並び替え |
| 供花の設定 | ベースURL、締切時間、カード決済の可否、業者情報、送信元・事業者情報・振込先 |

### 発注URL発行時の割引

葬儀ごとに割引を設定でき、そのURLから入った注文に自動適用される。

- 割引の種類: なし / 金額（円） / 率（％）
- 表示名を設定でき、発注画面と請求書に「ご紹介割引」などの名称で表示される
- 税抜の小計に対して適用し、消費税は割引後の金額で計算する（1注文ごとの適用）
- 金額はサーバー側（`create_flower_order`）で再計算するため、画面の値は信用しない

### アクセス制御の変更

ユーザー画面にログインが無いため、`funerals` / `flower_orders` / `flower_order_items` のRLSを
anonからの参照・更新を許可する形に変更した（`migrations/010_flower_internal_access.sql`）。
注文の作成は引き続き `create_flower_order` 経由のみ（INSERTは許可しない）。

メール送信（請求書・発注書）は、管理画面のログインか、対象の葬儀の発注トークンを知っていることを条件とする。

> anon key は公開サイトにも埋め込まれているため、鍵を取り出せる人は受注データを参照し得る。
> 確実に閉じるにはユーザー画面へのログイン導入が必要（2026-07-26時点では現状維持と判断済み）。
