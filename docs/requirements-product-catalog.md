# 商品マスタ（オプション画像の共通化）設計

作成日: 2026-08-13
対象: 見積画面のオプション、オプション画像カタログ、「？」ボタンの画像表示

## 1. 背景と課題

いまオプションの選択肢は `items.options`（JSONB配列）の中だけに存在し、商品コード（BC-21 など）は
**選択肢名の文字列に埋め込まれているだけ**です。

```
items
 └ options[]  { id, name: 'FO-01 (W1,800 カラー)', price, planPrices, allowedPlans, imagePaths }
```

このため、同じ商品が複数のアイテムに現れると別物として扱われます。

- 「祭壇 ＊1日葬」の BC-21 と「祭壇 ＊2日葬」の BC-21 は**別レコード**
- 画像も説明もそれぞれに登録が必要で、片方を直しても連動しない
- カタログページに同じ商品が何度も並ぶ

## 2. ゴール

- 商品（BC-21、YW-1、骨壺 …）を**1か所で管理**し、どのアイテム・どのプランから参照しても
  画像・説明・商品名が連動する
- 商品を**分類**（祭壇・骨壺・供花・骨壺覆い・その他）で束ね、カタログページで分類ごとに見られる
- 既存の商品コード（BC / FO / YW）はそのまま使う。コードが無いものは新規採番して割り当てる

## 3. 分類コード

分類は商品マスタの属性です。**既存コードの文字列は変更しません**（BC-21 は BC-21 のまま、分類だけ「祭壇」を当てる）。

| 分類 | 分類コード | 既存の商品コード | 新規採番 |
|---|---|---|---|
| 祭壇 | `ALTAR` | BC-21〜24、BC-39/40、FO-01〜04、FO-14、FO-18/19、FO-30〜35 | — |
| 後飾り祭壇 | `AFTER` | なし | `DA-01`〜 |
| 骨壺・骨箱 | `URN` | なし | `UR-01`〜 |
| 骨壺覆い | `URNCOVER` | なし | `UC-01`〜 |
| 供花 | `FLOWER` | YW-1、YW-2、YW-3 | `YW-4`〜（既存の採番を継続） |
| 遺影の額 | `PHOTO` | なし | `PF-01`〜 |
| お棺・仏衣 | `COFFIN` | なし | `CF-01`〜 |
| その他 | `OTHER` | なし | `OT-01`〜 |

- 分類コードは英大文字の識別子、画面には日本語名で出す
- 「お棺・仏衣」はご要望に無かったが、選択肢が9種類あり分類したほうが探しやすいので分けている。
  不要なら `OTHER` に寄せる
- 新規採番のプレフィックスは**分類ごとに固定**。コードを見れば分類が分かる（既存 BC/FO/YW は例外として許容）

## 4. データモデル

### 4.1 新テーブル `catalog_products`

| 列 | 型 | 内容 |
|---|---|---|
| `code` | text PK | 商品コード。`BC-21`、`YW-1`、`UR-01` |
| `category` | text NOT NULL | 分類コード（3章） |
| `name` | text NOT NULL | 商品名。例「白基調 W1,800」 |
| `description` | text | 説明。「[サイズ]約W1,800 白を基調とした…」 |
| `image_paths` | text[] | 画像。**唯一の置き場所**（バケットは既存の `item-images` を流用） |
| `display_order` | int | 分類内での並び |
| `is_active` | bool | 公開／非公開 |
| `created_at` / `updated_at` | timestamptz | |

### 4.2 選択肢（`items.options`）の変更

`DropdownOption` に `productCode?: string` を1つ足すだけです。

```ts
export interface DropdownOption {
  id: string;
  productCode?: string;   // ← 追加。catalog_products.code を参照
  name: string;           // マスタ紐付け時は表示に使わない（4.3参照）
  price: number;
  planPrices?: Record<string, number>;
  allowedPlans: PlanId[];
  imagePaths?: string[];  // 移行後は未使用。当面フォールバックとして残す
}
```

### 4.3 どちらが持つか

| 情報 | 持ち主 | 理由 |
|---|---|---|
| 商品名・説明・画像 | **商品マスタ** | 1か所直せば全箇所に連動する（本件の目的） |
| 価格・プラン別価格 | **選択肢** | 同じ BC-21 でも1日葬と2日葬で金額が違う（ランクアップ価格） |
| 対象プラン | **選択肢** | アイテムごとに出し分けが違う |
| 表示順 | **選択肢** | アイテムの中での並びはアイテム都合 |

商品名は**マスタを正**とする。選択肢側の `name` は移行時の記録として残すが、画面には出さない。

## 5. 移行

### 5.1 自動でやること（マイグレーション）

1. 全アイテムの選択肢名から `^([A-Z]{2})-(\d+)` を抽出し、見つかったコードで `catalog_products` を作成
   - 分類は暫定で `OTHER`、名前と説明は最初に見つかった選択肢のものを流用
   - 画像は、そのコードを持つ選択肢のうち**画像が入っている最初のもの**を採用
2. 抽出できた選択肢に `productCode` を書き込む
3. 同じコードで画像が食い違う選択肢があれば、移行ログに出して後で確認できるようにする

### 5.2 手でやること（管理画面）

- 自動作成された商品に**分類を当てる**（BC/FO → 祭壇、YW → 供花）
- コードが無かった選択肢（骨壺、遺影額、後飾り祭壇、お棺 …）を一覧から選び、新規コードを採番して紐付ける
  - 管理画面に「未割当の選択肢」一覧を用意し、そこから商品マスタを作れるようにする

移行後も `productCode` が空の選択肢は、従来どおり選択肢側の名前・画像で動く（後方互換）。
段階的に埋めていけるので、一斉切り替えは不要。

## 6. 画面

### 6.1 管理画面：商品マスタ管理（新規タブ）

- 分類タブ ＋ 一覧（コード・名前・画像・使用アイテム数）
- 追加／編集／コピー／削除。コピーと削除は確認ダイアログ（アイテム管理と同じ作法）
- 新規作成時は分類を選ぶと**次の連番コードを自動提案**（`UR-03` など）。手で直せる
- その商品を使っているアイテムを一覧表示し、削除前に影響が見える

### 6.2 管理画面：アイテム編集

- 各選択肢に「商品を選ぶ」欄を追加。分類で絞り込んでコードを選択
- 紐付けると、名前・説明・画像はマスタのプレビューを表示（その場では編集不可、マスタ側へのリンクを置く）
- 紐付けを外すと従来の入力欄に戻る

### 6.3 オプション画像カタログ

- 分類タブで絞り込み（祭壇／骨壺／供花 …）
- **同じ商品は1枚のカードに集約**（いまは同じ BC-21 が複数出る）
- 価格はプランを選んだときだけ出す。同じ商品で複数アイテムに載っている場合は「50,000円〜」のような幅表示

### 6.4 「？」ボタン（DetailModal）

- 選択中のグレードに `productCode` があればマスタの画像・説明を出す
- 無ければ現状どおり選択肢の `imagePaths` → `/images/` の順にフォールバック

### 6.5 価格はプラン別を引き継ぐ（先行対応）

商品マスタとは独立した既存の不具合。「？」からカタログを開くURLが `/?catalog=true&item=X` で
**プランを渡していない**ため、カタログ側は `planId='all'` で開き、選択肢の標準価格 `option.price` を表示する。
1日葬でランクアップして 100,000 円になる FO-01 が 50,000 円と出てしまう。お客様にお見せする画面なので先に直す。

- カタログを開くURLに選択中のプランを付ける（`&plan=PLAN_04`）
- カタログページは URL の `plan` を初期値にし、`planPrices[planId] ?? price` で表示する
- 併せて、選択中のグレード（`selectedGrade`）が DetailModal に渡っておらず、
  グレード別画像が優先表示されていない点も直す
- 進行管理画面（[CaseTaskPage](../components/tasks/CaseTaskPage.tsx)）からカタログを開く導線は、
  一覧が案件のプランIDを持っていないため据え置き（社内向けで価格提示の場面ではないため）。
  プランを渡す場合は `EstimateSummary` にプランIDを足す必要がある

商品マスタ導入後も、**価格は選択肢側（プラン別）から引く**という原則は変わらない（4.3参照）。

## 7. 実装ステップ

| # | 内容 | 単位 | 状況 |
|---|---|---|---|
| 0 | カタログを開くときのプラン引き継ぎ（6.5） | 表示 | 済 |
| 1 | `023_product_catalog.sql`（テーブル作成＋RLS＋自動移行） | SQL | 作成済・**未実行** |
| 2 | 型定義・`lib/catalogProducts.ts` | 共通 | 済 |
| 3 | 管理画面「商品マスタ」タブ | 管理 | 済 |
| 4 | アイテム編集の商品紐付けUI＋未割当一覧 | 管理 | 済 |
| 5 | カタログページを分類・商品単位に変更 | 表示 | 済 |
| 6 | DetailModal（？ボタン）をマスタ参照に | 表示 | 済 |
| 7 | 分類の割当作業（運用） | 運用 | これから |
| 8 | 旧 `options[].imagePaths` の掃除 | 後片付け | 未（当面フォールバックとして残す） |

### 実行手順

1. Supabase の SQL エディタで `migrations/023_product_catalog.sql` を実行する
   （末尾の確認クエリで、画像が食い違う選択肢・未割当の選択肢・作成された商品が一覧で出る）
2. フロントをデプロイする
3. 管理画面の「商品マスタ」で分類を当て、「未割当」タブから残りの選択肢を商品に紐付ける

SQL を実行する前にフロントを出しても、商品マスタが空なだけで従来どおり動く（表示は選択肢側にフォールバックする）。
